2. Resumen ejecutivo

Hallazgo: el formulario de verificación responde siempre el mismo mensaje ("No se puede acceder a esta información") ante una clave incorrecta, pero tarda mucho más cuando el código corresponde a un asistente real. Esa diferencia de tiempo permite distinguir los códigos válidos de los inexistentes sin conocer la clave y, contándolos, deducir la cantidad total de asistentes.

Riesgo para el negocio: un atacante no autenticado puede enumerar qué identificadores existen y obtener un dato agregado protegido (cantidad de asistentes), además de preparar ataques dirigidos posteriores (p. ej. fuerza bruta de clave solo sobre códigos reales).

Impacto principal sobre la tríada CIA: Confidencialidad. No se afectan integridad ni disponibilidad.

Severidad y prioridad: Media (CVSS v3.1 5.3). Prioridad de corrección media: la falla es fácil de explotar de forma remota y silenciosa, aunque la información expuesta en este laboratorio es acotada.

Acción recomendada: uniformar el tiempo de respuesta entre códigos válidos e inexistentes (ejecutar siempre una verificación de clave aunque el código no exista) y aplicar rate limiting.

3. Detalles técnicos

3.1 Descripción

El endpoint POST /index.php recibe codigo (3 dígitos) y clave. Ante una clave incorrecta devuelve un HTML idéntico para todos los códigos, por lo que el contenido de la respuesta no distingue códigos válidos de inexistentes. Sin embargo, el servidor solo ejecuta la verificación costosa de la clave (hash/consulta) cuando el código sí existe, lo que introduce una demora observable (~1 s) frente a los ~95 ms de un código inexistente. Esta discrepancia temporal es un canal lateral que permite enumerar los códigos válidos.

3.2 Componentes afectados

  • Aplicación / versión: Asistencia, backend PHP/8.0.30, detrás de Cloudflare.
  • Método y ruta HTTP: POST /index.php.
  • Parámetros involucrados: codigo, clave.
  • Roles o permisos necesarios: ninguno (acceso anónimo; no se requiere la clave).
  • Entorno y fecha de prueba: laboratorio autorizado, 2026-11-11.

3.3 Clasificación y causa raíz

  • CWE: CWE-208 (Observable Timing Discrepancy); relacionadas CWE-203 (Observable Discrepancy) y CWE-200 (Exposure of Sensitive Information).
  • CVE: No aplica (debilidad de configuración/implementación propia del laboratorio).
  • Referencia OWASP: A05:2021 — Security Misconfiguration (comportamiento observable que filtra información).
  • Causa raíz probable: la lógica de verificación hace trabajo distinto según exista o no el código (short-circuit para inexistentes), sin normalizar el tiempo de respuesta.

3.4 Impacto técnico y alcance

Bajo las condiciones verificadas, un atacante remoto y anónimo puede: (1) determinar qué códigos de 3 dígitos corresponden a asistentes reales midiendo el tiempo de respuesta, y (2) contar esos códigos para obtener la cantidad total de asistentes. No se demostró acceso a datos personales ni modificación o borrado de información; el impacto comprobado es de divulgación de información.

5. Prueba de concepto (PoC) — paso a paso

Objetivo: demostrar que el tiempo de respuesta revela los códigos válidos y permite contar los asistentes sin la clave.

Precondiciones: entorno de laboratorio autorizado; clave de prueba inválida; cookie de sesión propia (no se incluye en el reporte).

Herramientas: navegador + DevTools, Burp Suite (Intruder/Repeater), script propio en Python (medición secuencial de tiempos).

  1. Preparación: capturar en DevTools → Network la petición real POST /index.php con codigo y clave; descartar el ruido de Cloudflare (/cdn-cgi/rum).
  2. Solicitud inicial: enviar codigo=123&clave=xxxx y registrar la respuesta base.
  3. Observación del contenido: comprobar que el HTML es idéntico para distintos códigos (el cuerpo no discrimina).
  4. Modificación controlada: variar solo codigo en el rango completo 000–999, con clave fija inválida.
  5. Ejecución: medir el tiempo de respuesta de cada código (Intruder o script secuencial — no concurrente, para no corromper la medición).
  6. Verificación: clasificar por tiempo (≈95 ms = inexistente; ≈1 s = asistente válido) y re-medir los candidatos para descartar jitter de red.
  7. Cierre: contar los códigos válidos confirmados; ese total es la cantidad de asistentes. No se alteró ni persistió ningún dato.

6. Recomendaciones de remediación

6.1 Corrección inmediata

Normalizar el tiempo de respuesta: ejecutar siempre la verificación de clave (contra un hash dummy cuando el código no exista), de modo que válidos e inexistentes tarden lo mismo. Devolver el mismo mensaje y estado en todos los casos de error.

6.2 Medidas complementarias

  • Aplicar rate limiting y detección de enumeración (200–1000 peticiones secuenciales es un patrón detectable).
  • Requerir autenticación/autorización antes de evaluar la existencia del código.
  • Usar identificadores no secuenciales ni cortos (p. ej. UUID) cuando no deban ser adivinables.
  • Revisar que el framework no introduzca otras discrepancias observables (cabeceras, tamaños, tiempos).

6.3 Criterios de aceptación

  • ☐ El tiempo de respuesta es indistinguible entre código válido e inexistente.
  • ☐ Todos los errores devuelven el mismo mensaje y estado.
  • ☐ El rate limiting bloquea la enumeración masiva.
  • ☐ Se ejecutaron pruebas de regresión (timing + contenido).

Responsable sugerido: equipo de desarrollo backend. Fecha objetivo: a definir según prioridad.
